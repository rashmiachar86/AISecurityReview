Details: The workflow uses pull_request_target, which runs in the base repository context with secrets and a write-capable token even for pull requests from forks.

4. Discarded false positives

Not applicable to automated output: the scanner does not discard findings. Review each finding above and record false positives here during triage.

5. Not covered by static scan

  • Branch protection and required reviews on the default branch
  • GitHub secret scanning and push protection enabled
  • Who can trigger workflow_dispatch / approve environments for secret-bearing jobs
  • Token, GitHub App and OAuth app scopes, expiry and rotation status
  • Package maintainer 2FA and registry / CI platform access reviews
  • Git history (run with --history on a real clone) and contents of vendored binaries

6. Recommended next steps

  1. Secret echoed to build log (25, high): Never print secrets. Rely on masking only as a backstop; remove the command.
  2. Credentials embedded in URL / connection string (5, high): Revoke and rotate the credential now, remove it from code, and load it at runtime from a secret manager or CI secret store. If it was committed, also purge git history.
  3. Untrusted GitHub context interpolated (script injection) (4, high): Pass the value through an `env:` variable and reference it as a shell variable instead of inlining `${{ }}` into `run:`/`script:`.
  4. pull_request_target trigger (1, high): Never check out or run untrusted PR code in this context. Use `pull_request` or split into an unprivileged build and a privileged, artifact-only follow-up workflow.
  5. Credential file copied into image (1, high): Do not copy credentials into images; add to .dockerignore and mount at runtime.
